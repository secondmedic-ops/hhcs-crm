# Draft for review: Book My Medicare technical interface request

**Status:** internal draft, 15 October 2026. Not sent. No recipient address or technical contact has been supplied. No authorization to contact BMM is implied.

We are preparing a connection between Book My Medicare's operational system and the HHCS CareDesk CRM operated by SecondMedic. SecondMedic will remain the operational point of contact. We need to confirm your actual supported interface before selecting an integration method. Publication of our HHCS-side preparation is authorized; activation and patient exchange await the agreed interface and acceptance process. Please use synthetic examples only during technical review.

Please provide the following information and supporting documentation.

1. **System and technical ownership.** Software/product name, edition/version, whether operated by BMM or a third party, technical contact and escalation contact, production onboarding owner and support hours.
2. **API contract and environments.** Current API specification/version, changelog/deprecation policy, documented base URLs for sandbox and production, sandbox account availability, synthetic test data policy, network/IP restrictions and onboarding prerequisites. Do not send production passwords or tokens in a document or email; agree a secure credential channel separately.
3. **Connection direction.** Can your server retrieve approved leads from an authenticated HHCS API and post receipt/status/resource updates? Can it securely obtain and refresh a dedicated Supabase Auth login token? If you require HHCS to call your API, identify the mandatory operations and supported callback or polling mechanism. If there is no usable API, describe a supported secure, versioned file exchange and its receipt process.
4. **Authentication and permissions.** Supported protocol, token lifetimes/refresh, scopes/account permissions, tenant/account binding, sandbox/production separation, credential issue/rotation/revocation, overlap during rotation and safe non-patient identity/connection-test endpoint. Confirm whether a machine account can be restricted to HHCS-assigned orders only.
5. **Lead/order operations.** Actual documented create, retrieve/search, list, amend, cancel/withdraw, reopen and history endpoints; required fields; response examples; external reference rules; whether one HHCS referral can map to one order with revisions or needs multiple orders; limitations on adding/dropping services after acceptance or dispatch.
6. **Idempotency and uncertain outcomes.** Does create/amend/cancel accept an idempotency key, how long is it retained, and what happens for the same key with different content? Can orders be looked up by a unique HHCS-supplied reference after a timeout? How do we distinguish not created from still processing? What recovery procedure prevents duplicate orders where neither feature exists?
7. **Receipt, acceptance and status meanings.** Separate persisted receipt from service acceptance. Provide every literal status/event code and legal transition, terminal/reopen rules, partial acceptance, decline/cancellation reasons, source entity versions/sequences and actual event-time fields. How are unknown, delayed or reordered events resolved? Can a revision and HHCS event ID be echoed in acknowledgements?
8. **Service and resource model.** Service catalogue identifiers, allowed units and conversions, quantity meaning, 12-hour/24-hour coverage, repeated visits/shifts, concurrent staff, rental start/end conventions, equipment delivery/install/use/return, staff replacement and resource assignment identifiers. Can each event identify the HHCS item and required occurrence/shift? How is partial fulfilment/completion represented?
9. **Amendment, hold and cancellation.** How does your system stop new fulfilment after agreement/sharing is withdrawn? How is the exact revision/affected quantity acknowledged? What can happen after dispatch, arrival or duty start, and what requires manual intervention? What is the documented stop/cancel response target? How do we confirm cessation/return without assuming a local HHCS cancellation instantly stops your work?
10. **Webhooks, if supported.** Event catalogue and sample payloads, webhook registration, raw-body signature algorithm/canonicalization/header/key handling, timestamp/replay window, unique event IDs, delivery order guarantees, response status/acknowledgement rules, retry schedule/limit, redelivery tools, key rotation and any documented source network restrictions.
11. **Lists and polling.** Pagination/cursor semantics, consistent snapshots, updated-since/history filters, deletion/hold/cancellation tombstones, cursor/event retention, checkpoint recovery, maximum page size and recommended polling interval. How can we reconcile all active orders/resources if callbacks are missed?
12. **Operational limits and errors.** Rate/concurrency limits per account/endpoint, request/response size limits, timeouts, asynchronous operations and polling, error schemas/codes, 429/Retry-After behavior, maintenance/outage notification, timestamp/timezone and daylight/date interval conventions.
13. **Minimum data and attachments.** Which patient/contact/address fields are strictly necessary for each service? Are hospital/age/gender or clinical fulfilment instructions actually required? We will not transfer internal clinical assessments, call recordings, other-provider services, procurement costs or margins. If attachments are indispensable, specify purpose, allowed type/size, secure transfer/download expiry, access controls, storage/retention and deletion process. Extra data categories need separate review.
14. **Acceptance and production onboarding.** Required certification/UAT cases, sandbox-to-production differences, account provisioning, security/data-sharing agreements, approved support/escalation channel, cutover window, rollback/disable procedure and completion sign-off. Confirm how synthetic sandbox tests prove create/link, receipt, acceptance/decline, amendment/withdrawal/cancel, resource progress, duplicate handling and timeout recovery.

HHCS already has a prepared, disabled-by-default proposed interface: `GET /api/v1/bmm/leads` and `POST /api/v1/bmm/leads/{id}/status`, using a dedicated BMM provider identity. It returns scoped included service items and accepts idempotent lead status events. It is not yet a complete resource/revision/receipt contract or a claim of compatibility with your system. We can share the reviewed contract and agree the smallest supported extension once you confirm the capabilities above.

Please return documentation links/files, synthetic request/response examples, unsupported operations and your preferred method. We will then agree a field/status mapping and sandbox test plan before any production deployment, activation or patient exchange.
